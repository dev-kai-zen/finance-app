# Kaizen Finance performance audit

**Android release 1.8.0 (22) · Source revision `a307370` · November 19, 2026**

## 1. Executive Summary

**Fix the Android widget refresh cycle first.** A local database change listener watches the settings table. Its callback calculates the financial widget snapshot and writes a new timestamp to that same table. On a fresh Android emulator with zero widgets pinned, the snapshot kept changing while the screen sat idle in airplane mode. The calculation includes Home's recent transactions, category breakdown and net-worth chart history, although the widgets display totals. This gives an otherwise idle app recurring opportunities to delay a press.

**The largest scaling problem is the cost of asking for a few transactions.** Home requests five, then loads, enriches, groups and sorts the whole active ledger before taking five. In an isolated host run of the production service, the median grew from **7.86 ms and 6 SQL statements at 100 rows** to **3,608 ms and 404 statements at 100,000**. Home performs that work twice per focus refresh. The Transactions screen's 50-row display limit also comes after retrieval. These results identify specific work to remove. Host timings include a test SQLite adapter and cannot predict phone latency.

**There are two FAB interactions.** On Home and Transactions the plus first opens a speed dial using local React state. Choosing Manual Entry mounts a native slide modal and initializes the form. Neither ordinary press handler queries SQLite. A release recording showed the form title by **319 ms** after Manual Entry first appeared pressed with 31 ledger rows, and by **675 ms** with 10,000. These are single visual observations with an 85 ms test hold. The likely contributors are JS contention from existing work, followed by form rendering and native presentation. A first-use dashboard walkthrough can separately intercept the touch entirely. The relative contribution of each thread to an individual delayed tap still requires a trace.

**Recommended order after approval**

1. Break widget self-invalidation and compute only the three widgets' inputs.
2. Bound Home's recent-transactions query and compute its shared summary once per refresh.
3. Page the transaction feed in SQLite by logical item and fetch Trash and statistics only for consumers that need them.
4. Give each committed mutation one refresh owner and coalesce obsolete refresh requests.
5. Build net-worth history with one chronological pass over the necessary ledger rows.

The full priority order, including form, search, account and report work, is in sections 3 and 9. The audit used synthetic records, a disposable emulator, and a host in-memory database. Physical-device input latency, React commit durations and post-optimization figures are **Not Measured**. This report is the only repository change.

## 5. Database Performance Findings

**Cost of a refresh.** For the unfiltered active ledger, let A be matching raw legs and G the number of logical rows after grouping. The active list issues four fixed statements (joined ledger, chronological account rows, chronological pocket rows, attachment counts), plus ⌈A/500⌉ label reads and ⌈G/500⌉ split reads. The deleted list uses the same shape, including the three supporting reads with empty Trash. The stats query adds one. With N active standalone transactions and empty Trash this gives **9 + 2 × ⌈N/500⌉** per feed refresh, verified from the prepared statements. This excludes separately mounted accounts, presets, categories and labels. It also excludes UI sorting, view construction and garbage collection after return. [Feed repository](src/modules/transactions/repositories/transactions.repository.ts) · [Split reads](src/modules/transactions/repositories/transaction-entries.repository.ts) · [Label reads](src/modules/labels/repositories/transaction-labels.repository.ts)

**Actual SQLite plans.** These are host SQLite 3.47.2 plans on a fresh migrated fixture at 100k active rows, with its original indexes and no manual ANALYZE. Data distributions and Android SQLite versions can change planner decisions.

| Query inspected | Observed plan detail | Consequence |
| --- | --- | --- |
| Active feed ordered by occurred/created | `SCAN transactions`, primary-key searches of joined tables, `USE TEMP B-TREE FOR ORDER BY` | Reads the full ledger and sorts globally. Existing account+date and category+date indexes serve scoped predicates. |
| Ordered account running balances / historical deltas | `SCAN transactions` and temporary sort | Chronology is reconstructed for old rows even when the caller displays only five. |
| Empty Trash ordered by deleted/occurred | `SCAN transactions`, temporary order structure | Asking on every focus pays the scan even if nothing is deleted. Removing the read from normal focus comes first. |
| All-time stats / balance totals | Stats used a scan and temp B-tree for the distinct transfer count. Per-account sum scanned via `transactions_account_occurred_at_index`. | SQL produces compact aggregates. Computing rarely consumed metrics on every refresh still visits historical rows. |

**Index experiment.** In a separate in-memory copy we compared `SELECT id FROM transactions WHERE deleted_at IS NULL ORDER BY occurred_at DESC, created_at DESC, id DESC LIMIT 5` with and without a partial index on `(occurred_at DESC, created_at DESC, id DESC) WHERE deleted_at IS NULL`. The baseline used a scan and temporary sort. The candidate scanned the index in order and returned identical five IDs. Six host runs including preparation took 6.42–7.37 ms and 0.011–0.042 ms respectively. This measures only selection of five standalone IDs. Group-aware selection, historical balances, details, migration costs, insert throughput and storage need separate benchmarks. Existing group-ID, transaction-label, split-entry and attachment indexes already cover key lookups. Consider a deleted-only index only if paged Trash is still slow. Any production index would need a named Drizzle migration, size/write tests, safe rollout on large databases and a tested inverse `DROP INDEX`. [Transaction schema](src/infrastructure/database/schema/transactions.ts)

**Query ownership and integrity.** The account balance SUM and pocket aggregate are already set-based. Budgets have a grouped category/currency service worth reusing. Home's breakdown directly joins transaction/category tables, and some account imports deep-link into another module. Place new scoped queries behind the owning transactions service. Compare the existing dashboard and report semantics before consolidating them. Home groups parent transactions by their category, while the report explicitly handles split entries. Combining converted totals can change results when per-row rounding differs. [Dashboard repository](src/modules/dashboard/repositories/dashboard.repository.ts) · [Category report](src/modules/transactions/services/get-category-breakdown.service.ts) · [Budget aggregation](src/modules/transactions/services/get-category-expense-summary.service.ts)

**Statements and transactions.** The application uses one runtime connection with explicit transactions for related writes. The SQL monitor finalizes the statement it explicitly prepares in a `finally` block. Drizzle owns statement lifetime for repository queries. No evidence established an application statement leak. For bulk paths, count preparations and measure retained native memory across cycles before introducing statement caching. Backup/restore uses serialized snapshots, WAL checkpointing, a lock and rollback handling. Preserve database replacement notifications and the migration gate.

## 7. Memory and JavaScript Thread Findings

- **Largest allocations.** A feed refresh can hold joined rows, two running-balance maps, attachment/label maps, mapped items, transfer groups, split metadata and a sorted output; the screen then makes another list copy. A preserved route can retain its own data after navigation. At 100k rows, the dominant remedy is to bound retrieval. Narrowing the SectionList window cannot reclaim arrays still referenced by hooks.
- **Work after paint.** A double animation frame changes when synchronous work begins. It does not yield during a full scan, JS sort or date loop. Focus changes can queue work for a screen the user has already left. Capture a JS sample and a FrameTimeline trace across rapid route changes.
- **Bulk and images.** Backups may hold serialized bytes, normalized copies, archive bytes and rollback bytes during restore. Notes and receipt photos add native image memory. Measure native PSS, graphics and JS heap separately for repeated form/open/close, image preview/dismiss, export/import and backup/restore. Keep encrypted backup processing and rollback intact.
- **Lifecycle.** Widget, reminder and Quick Sync effects remove their subscriptions. Shake gestures disable the accelerometer when inactive or gated, and the form skeleton stops its animation on cleanup. The widget issue is a live subscription receiving its own writes. One larger memory snapshot after a modal open cannot establish a leak. Repeated cycles and retained-object paths are required.
- **Frame budget.** A 60 Hz display allows about 16.7 ms per frame and 120 Hz about 8.3 ms; JS shares the interaction budget with React, native layout and presentation. One measured 10k host recent-items call occupied hundreds of milliseconds. Only release traces on target hardware can establish sustained frame delivery.

## 8. Recommended Architecture Improvements

1. **Keep financial posting local and atomic.** The mutation service prepares attachments, posts the transaction or transfer, records related metadata and enqueues attachment work within the same transaction. Drive and attachment retries belong outside the UI wait path. On the emulator, a PHP 1.00 expense saved in airplane mode and survived a process restart. The ledger grew by one, the stored signed value was −100, and `PRAGMA foreign_key_check` returned no rows. This exercises one ordinary save. Transfers, sync interruption and restore need their own regression cases. [Posting service](src/modules/transactions/services/record-transaction.service.ts) · [Outbox](src/infrastructure/sync/queue/sync-operations.repository.ts)
2. **Separate display queries by the question they answer.** Give Home recent logical items, Calendar a time window, search a bounded preview, and widgets current totals. Let Transactions own ledger semantics. Account and pocket services should supply one scoped snapshot per consumer operation. Views can load fuller detail when selected. Preserve the exact balance *after* a historical posting using a date/created/id anchor and preceding account/pocket sums.
3. **Reuse within a refresh before caching across screens.** One Home refresh can reuse balances, rates and monthly totals. If later measurements justify longer-lived caching, key snapshots by workspace/database revision, account/pocket, period, currency/rate revision and relevant filters. Invalidate after successful create, edit, backdate, delete, restore, scheduled post, bulk import, settings/rate change and database replacement. An edit invalidates both its old and new scopes. Include date rollover. Publish only committed values.
4. **Preserve per-report definitions.** Cash-flow transfers, standalone fees, signed liabilities, split parent/child sums, labeled totals, local month boundaries and exchange-rate rounding have different meanings. Prefer existing grouped SQL where semantics already match. A changed exchange rate or opening balance can invalidate history without any new transaction. Materialized balances would add recovery and repair obligations. Bound the queries and measure first.
5. **Keep background work observable.** Count widget recomputations, financial reads and refreshes per committed action, with a reason and elapsed duration. Use local profiling flags on synthetic data for detailed traces. Keep descriptions, amounts, account names and SQL bindings out of production analytics. The existing telemetry privacy controls provide an appropriate boundary.

One freshness case deserves an explicit test before removing duplicate events. The Transactions feed refreshes on focus and after its own mutations. Its hook emits the global transaction event but does not subscribe to it. A save from a different modal host while the feed retains focus can therefore leave old rows visible until its next refresh. Capture this scenario alongside Home's duplicate refresh. Reducing one consumer's work should still deliver the update to the other.

## 10. Quick Wins

- **Stop the widget's self-generated settings invalidation.** Keep genuine preference/entitlement updates explicit and verify a quiet idle minute. The debounce alone cannot stop a write that schedules the next callback.
- **Remove the second form label refresh.** Keep the explicit refresh after editing labels. Two initial list queries should become one on an already focused form.
- **Give an empty Trash result a fast exit.** Skip enrichment for zero deleted records, then move the full Trash query to its actual consumer. Check the Trash count and restore workflow.
- **Eliminate the duplicate Home save refresh and quick-entry event.** Confirm the remaining notification reaches mounted consumers before removing either path.
- **Replace the Notes existence check with a one-row query.** Verify the difference between an empty workspace and zero matches without loading attachment metadata for all notes.

### Reproduce the host baseline

The following is an isolated benchmark harness for this revision. Save it **outside the repo** as `kaizen-audit.cjs`, run it from the repository root with `node --expose-gc --max-old-space-size=6144 <absolute-path-to-kaizen-audit.cjs>`, and use only in-memory databases. const path = require("node:path");
const Module = require("node:module");
const file = path.resolve("src/modules/accounts/__tests__/accounts.test.cjs");
const boundary = "beforeEach(() => { connect(); migrate(); });";
const setup = fs.readFileSync(file, "utf8").split(boundary)[0]

function benchmark() {
